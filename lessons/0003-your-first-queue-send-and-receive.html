<dependency>

Infrastructure Detail: What the Artemis Starter Auto-Configures

When Spring Boot sees spring-boot-starter-artemis on the classpath, it automatically creates:

  • ConnectionFactory — configured from your spring.artemis.* properties
  • JmsTemplate — wired to that ConnectionFactory, ready to send messages
  • JmsListenerContainerFactory — creates listener containers for every @JmsListener

You don't create any of these beans. Spring Boot does it for you.

Step 2: Configure the Broker Connection

Replace the contents of src/main/resources/application.yml (rename from .properties if needed):

# application.yml
spring:
  artemis:
    mode: native                          # connect to external broker (our Docker container)
    broker-url: tcp://localhost:61616     # TCP connection to Artemis on port 61616
    user: admin                           # credentials we set in docker run
    password: admin

# Application settings
server:
  port: 8080

app:
  queue:
    notification: notification.queue      # our queue name — used in code via @Value

What Each Property Means at the Network Level

Property What Happens
spring.artemis.mode=native Tells Spring Boot to connect to an external broker over TCP (not start an embedded one)
spring.artemis.broker-url The TCP address of the broker. The ConnectionFactory uses this to open a socket.
spring.artemis.user/password Sent during TCP handshake. The broker authenticates your app before allowing messages.
app.queue.notification Custom property — not Spring magic. We'll inject it with @Value so the queue name isn't hardcoded.

Step 3: Build the Sender

Create src/main/java/com/learning/notificationhub/service/NotificationSender.java:

package com.learning.notificationhub.service;

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.jms.core.JmsTemplate;
import org.springframework.stereotype.Service;

@Service
public class NotificationSender {

    private static final Logger log = LoggerFactory.getLogger(NotificationSender.class);

    private final JmsTemplate jmsTemplate;

    @Value("${app.queue.notification}")
    private String queueName;

    public NotificationSender(JmsTemplate jmsTemplate) {
        this.jmsTemplate = jmsTemplate;
    }

    public void send(String message) {
        log.info("📤 Sending to [{}]: {}", queueName, message);
        jmsTemplate.convertAndSend(queueName, message);
        log.info("✅ Message sent successfully");
    }
}

What Happens When send() is Called

Let's trace the entire journey of a message from your code to the broker's disk:


  Your Code                    JmsTemplate (Spring)               Broker (Artemis)
  ═══════════                  ═══════════════════                ═══════════════════

  send("Hello")
       │
       ▼
  convertAndSend()
       │
       ├──→ 1. Gets Connection from ConnectionFactory
       │       (opens TCP socket to localhost:61616 if not cached)
       │
       ├──→ 2. Creates a Session on that Connection
       │       (single-threaded context for this operation)
       │
       ├──→ 3. Creates a MessageProducer for "notification.queue"
       │
       ├──→ 4. Wraps "Hello" in a TextMessage
       │
       ├──→ 5. Calls producer.send(textMessage) ──TCP──→  Broker receives bytes
       │                                                   │
       ├──→ 6. Closes Session, returns Connection          ├──→ Writes to journal
       │       to pool (or closes it)                      │    (disk persistence)
       │                                                   │
       ▼                                                   ├──→ Adds to queue
  Method returns                                           │    "notification.queue"
  (your code continues)                                    │
                                                           ▼
                                                    Message waiting for
                                                    a consumer to pick it up

Step 4: Build the Listener

Create src/main/java/com/learning/notificationhub/listener/NotificationListener.java:

package com.learning.notificationhub.listener;

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.jms.annotation.JmsListener;
import org.springframework.stereotype.Component;

@Component
public class NotificationListener {

    private static final Logger log = LoggerFactory.getLogger(NotificationListener.class);

    @JmsListener(destination = "${app.queue.notification}")
    public void onNotification(String message) {
        log.info("📩 Received notification: {}", message);

        // In a real app, you'd process the notification here:
        // - Send an email
        // - Push to a mobile device
        // - Write to a database
    }
}

How @JmsListener Works at the Infrastructure Level

What Happens When Your App Starts
  1. Spring scans for @JmsListener annotations
  2. For each one, it creates a listener container — a background thread that opens a Connection to the broker
  3. The container registers a MessageConsumer for notification.queue with the broker
  4. The broker now knows: "when a message arrives on notification.queue, push it to this consumer"
  5. When a message arrives, the broker sends it over TCP to your app
  6. The listener container deserializes it and calls your onNotification() method

Key point: This is a push model, not polling. The broker initiates delivery. Your app doesn't loop asking "any messages?"

Step 5: Build the REST Controller

Create src/main/java/com/learning/notificationhub/controller/NotificationController.java:

package com.learning.notificationhub.controller;

import com.learning.notificationhub.service.NotificationSender;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.*;

@RestController
@RequestMapping("/api")
public class NotificationController {

    private final NotificationSender sender;

    public NotificationController(NotificationSender sender) {
        this.sender = sender;
    }

    @PostMapping("/notify")
    public ResponseEntity<String> notify(@RequestBody String message) {
        sender.send(message);
        return ResponseEntity.ok("Notification sent: " + message);
    }
}

This is the entry point. An HTTP POST to /api/notify triggers the whole messaging flow:

HTTP POST → Controller → NotificationSender → JmsTemplate → TCP → Broker → Queue → @JmsListener → Console log

What You Should See

In your Spring Boot console:

INFO  ... 📤 Sending to [notification.queue]: Hello from Lesson 03!
INFO  ... ✅ Message sent successfully
INFO  ... 📩 Received notification: Hello from Lesson 03!

The send and receive happen almost instantly because both the producer and consumer are in the same app. But the message did travel out to the broker and back — it's not a shortcut.

Verify in the Broker Console

Open http://localhost:8161 (login: admin/admin) and look at:

  • Queues → notification.queue — you'll see it was auto-created
  • Messages Enqueued — count of messages sent to this queue
  • Messages Dequeued — count of messages consumed (should match enqueued)
  • Consumers — should show 1 (your @JmsListener)

Step 7: Experiment (Desirable Difficulty)

Don't just run it once and move on. Try these experiments to build real understanding:

🧪 Experiment A: Stop the Consumer

  1. Stop your Spring Boot app (Ctrl+C)
  2. Send a message via the Artemis web console directly to notification.queue
  3. Check the queue — the message should be waiting (Message Count = 1)
  4. Restart your Spring Boot app
  5. Watch the console — the queued message is immediately delivered to your listener

This proves: The broker stores messages until a consumer is ready. This is the resilience you explained in the grill session.

🧪 Experiment B: Send Multiple Messages Rapidly

# Send 5 messages in quick succession
for i in 1 2 3 4 5; do
  curl -s -X POST http://localhost:8080/api/notify \
    -H "Content-Type: text/plain" \
    -d "Notification #$i"
done

Watch: All 5 arrive at the listener. Each goes through the full journey: your code → TCP → broker → TCP → listener.

🧪 Experiment C: Inspect the TCP Connection

While the app is running, open a terminal and run:

# See the actual TCP connection from your app to the broker
lsof -i :61616

You'll see: A TCP socket between your Java process and port 61616. This is the real Connection object from JMS — the one that ConnectionFactory created.

Knowledge Check

Which Spring Boot starter auto-configures the ConnectionFactory, JmsTemplate, and listener infrastructure for Artemis?

  • spring-boot-starter-artemis
  • spring-boot-starter-activemq
  • spring-boot-starter-jms
  • spring-boot-starter-messaging

What does spring.artemis.mode=native tell Spring Boot to do?

  • Connect to an external Artemis broker running on a separate process over TCP
  • Start an embedded Artemis broker inside the application's own JVM process
  • Use the native operating system's messaging APIs instead of the JMS protocol
  • Compile the application to a native binary using GraalVM for better performance

Your @JmsListener consumer is registered but no messages are arriving. The broker console shows messages sitting in the queue. What's the most likely cause?

  • The destination name in @JmsListener doesn't match the actual queue name on the broker exactly
  • The broker is running out of memory and cannot push messages to any connected consumers
  • The JmsTemplate and @JmsListener are conflicting with each other on the same queue
  • You need to manually call connection.start() in your application before messages flow

When does Artemis auto-create the notification.queue destination?

  • When the first message is sent to it or the first consumer subscribes to it, whichever happens first
  • When you define the queue name in application.yml and the Spring Boot application starts
  • You must manually create it in the Artemis web console before any messages can be processed
  • When the Docker container starts, it pre-creates all queues from its configuration XML files
