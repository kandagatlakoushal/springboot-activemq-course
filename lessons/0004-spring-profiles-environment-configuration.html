Part 1: The Problem Profiles Solve

Your Current Situation

Right now, your Notification Hub has one application.yml with everything hardcoded:

# Your current application.yml — EVERYTHING in one place
spring:
  artemis:
    mode: native
    broker-url: tcp://localhost:61616      # ← only works on YOUR laptop
    user: admin                            # ← dev credentials
    password: admin

server:
  port: 8081                               # ← your dev port

app:
  queue:
    notification: notification.queue

This works fine on your laptop. But what happens when this goes to production?


  THE DEPLOYMENT PROBLEM
  ══════════════════════

  Your Laptop (dev)                     Production Server
  ──────────────────                    ──────────────────
  Broker: localhost:61616               Broker: broker.prod.spglobal.com:61616
  User:   admin                         User:   svc-notification-prod
  Pass:   admin                         Pass:   (rotated secret)
  Port:   8081                          Port:   8080
  Queue:  notification.queue            Queue:  prod.notification.queue
  Logs:   DEBUG level                   Logs:   WARN level

  ❌ If you hardcode "localhost:61616" into your code, it will NEVER
     connect in production. You'd have to change code for each deploy.

  ✅ Solution: Spring Profiles — ONE codebase, MULTIPLE configurations.
Interview Insight

"Spring Profiles let us deploy the exact same JAR artifact to dev, staging, and production. The environment tells the app which profile to activate, and the app loads the right configuration. No code changes, no rebuilds — just a runtime switch."

Part 2: How Profiles Work

The Property Resolution Model

Spring Boot loads properties in a layered model. Higher layers override lower ones:


  PROPERTY RESOLUTION ORDER (highest priority wins)
  ══════════════════════════════════════════════════

  ┌─────────────────────────────────────────┐
  │  1. Command-line arguments              │  ← highest priority
  │     --spring.artemis.broker-url=...     │     (useful for one-off overrides)
  ├─────────────────────────────────────────┤
  │  2. Environment variables               │  ← second highest
  │     SPRING_ARTEMIS_BROKER_URL=...       │     (common in Docker/Kubernetes)
  ├─────────────────────────────────────────┤
  │  3. Profile-specific config             │  ← third
  │     application-dev.yml                 │     (the main mechanism)
  │     application-prod.yml                │
  ├─────────────────────────────────────────┤
  │  4. Base application.yml                │  ← lowest priority
  │     (shared defaults for all envs)      │     (always loaded)
  └─────────────────────────────────────────┘

  Example: If application.yml says port=8080
           and application-dev.yml says port=8081
           and you pass --server.port=9090 on CLI
           → The app runs on port 9090 (CLI wins)

The Merge Rule

The base application.yml is always loaded. The profile-specific file merges on top:

# application.yml (base — ALWAYS loaded)
spring:
  application:
    name: NotificationHub
app:
  queue:
    notification: notification.queue
logging:
  level:
    root: INFO

# application-dev.yml (loaded ONLY when profile = "dev")
# These properties OVERRIDE or ADD to the base
spring:
  artemis:
    mode: native
    broker-url: tcp://localhost:61616
    user: admin
    password: admin
server:
  port: 8081
logging:
  level:
    com.learningPath: DEBUG             # verbose logs in dev

# application-prod.yml (loaded ONLY when profile = "prod")
spring:
  artemis:
    mode: native
    broker-url: tcp://broker.prod.internal:61616
    user: ${ARTEMIS_PROD_USER}          # from environment variable
    password: ${ARTEMIS_PROD_PASSWORD}  # NEVER hardcode prod creds
server:
  port: 8080
logging:
  level:
    root: WARN                          # quiet logs in prod

What the app sees when running with dev profile:

Property Source Value
spring.application.name base (no override) NotificationHub
app.queue.notification base (no override) notification.queue
spring.artemis.broker-url application-dev.yml tcp://localhost:61616
server.port application-dev.yml 8081
logging.level.com.learningPath application-dev.yml DEBUG

Properties from the base file stay. Properties from the profile file override or add. That's the merge.

Part 3: Activating Profiles

Three ways to tell Spring Boot which profile to use. Each maps to a different deployment scenario:

Method 1: Command-Line Argument

# Run with dev profile
java -jar notification-hub.jar --spring.profiles.active=dev

# Or with Maven
./mvnw spring-boot:run -Dspring-boot.run.profiles=dev

When to use: Local development, quick testing. You type it yourself.

Method 2: Environment Variable

# Set before running the app
export SPRING_PROFILES_ACTIVE=prod
java -jar notification-hub.jar

# In Docker (most common in production)
docker run -e SPRING_PROFILES_ACTIVE=prod my-app:latest

When to use: Production deployments, Docker, Kubernetes. The environment controls the profile, not the developer.

Method 3: In the Base application.yml

# application.yml
spring:
  profiles:
    active: dev   # default profile — overridden by CLI or env var

When to use: Setting a sensible default for local development. The developer doesn't have to remember to pass a flag.

Infrastructure Detail: How This Works in Enterprise

At companies like S&P Global MI, you never set the profile in the YAML file committed to Git. Instead:

  • Dev: IDE launch config sets --spring.profiles.active=dev
  • Staging/QA: Kubernetes Deployment.yaml sets the env var SPRING_PROFILES_ACTIVE=staging
  • Production: Kubernetes sets SPRING_PROFILES_ACTIVE=prod

The JAR artifact is the same binary deployed to every environment. Only the profile activation changes.

Part 4: Refactor Your Notification Hub

Let's upgrade your project. You'll split your current single application.yml into three files.

Step 1: Refactor application.yml (Base — Shared Config)

Keep only environment-agnostic properties here:

# src/main/resources/application.yml
# BASE CONFIG — shared across ALL environments
# No broker URLs, no credentials, no ports here!

spring:
  application:
    name: NotificationHub
  profiles:
    active: dev                         # default to dev for local development

app:
  queue:
    notification: notification.queue    # queue name is the same everywhere

Step 2: Create application-dev.yml

Create a new file src/main/resources/application-dev.yml:

# src/main/resources/application-dev.yml
# DEV PROFILE — local Docker Artemis broker

spring:
  artemis:
    mode: native
    broker-url: tcp://localhost:61616
    user: admin
    password: admin

server:
  port: 8081

logging:
  level:
    com.learningPath: DEBUG             # see detailed logs during development

Step 3: Create application-prod.yml

Create src/main/resources/application-prod.yml:

# src/main/resources/application-prod.yml
# PROD PROFILE — production Artemis broker

spring:
  artemis:
    mode: native
    broker-url: tcp://broker.prod.internal:61616
    user: ${ARTEMIS_PROD_USER}           # injected from env var at runtime
    password: ${ARTEMIS_PROD_PASSWORD}   # NEVER commit real creds to Git

server:
  port: 8080

logging:
  level:
    root: WARN                           # only warnings and errors in prod
    com.learningPath: INFO               # minimal app logs in prod

Step 4: Create application-test.yml (Bonus)

Create src/main/resources/application-test.yml for integration tests:

# src/main/resources/application-test.yml
# TEST PROFILE — embedded broker (no Docker needed)

spring:
  artemis:
    mode: embedded                       # starts broker INSIDE your JVM

server:
  port: 0                                # random port (avoids conflicts in CI)

logging:
  level:
    root: WARN
Infrastructure Detail: Embedded Mode

When spring.artemis.mode=embedded, Spring Boot starts a mini Artemis broker inside your application's JVM. No Docker, no external process. The broker lives in memory, dies when your app dies.

This is perfect for tests — every test run gets a clean broker with no leftover messages. To enable embedded mode, you need one extra dependency:

<!-- Add to pom.xml for embedded broker support -->
<dependency>
    <groupId>org.apache.activemq</groupId>
    <artifactId>artemis-jakarta-server</artifactId>
    <scope>test</scope>            <!-- only for testing, not production -->
</dependency>

Step 5: Run & Verify

Your Project Structure Now

src/main/resources/
├── application.yml              # shared base (app name, queue names)
├── application-dev.yml          # dev: localhost broker, port 8081, DEBUG logs
├── application-prod.yml         # prod: remote broker, port 8080, WARN logs
└── application-test.yml         # test: embedded broker, random port

Run with Dev Profile

# Option A: Maven (uses default from application.yml)
./mvnw spring-boot:run

# Option B: Explicit profile
./mvnw spring-boot:run -Dspring-boot.run.profiles=dev

Look for this in the startup logs:

# This confirms which profile is active
The following 1 profile is active: "dev"

Test That Everything Still Works

# Send a notification (same as Lesson 03)
curl -X POST http://localhost:8081/app/notify \
  -H "Content-Type: text/plain" \
  -d "Profile test from dev!"

You should see the same send + receive logs, but now with DEBUG level logging active.

Step 6: Experiment (Desirable Difficulty)

🧪 Experiment A: Switch Profiles on the Fly

  1. Stop the app
  2. Run with prod profile: ./mvnw spring-boot:run -Dspring-boot.run.profiles=prod
  3. Watch it fail to connect — because broker.prod.internal:61616 doesn't exist on your network
  4. This proves the profile switch is real — the app tried to connect to a different broker

This demonstrates: Same code, different behavior, controlled by a single flag.

🧪 Experiment B: Override with Environment Variable

# Even with prod profile, override the broker URL
SPRING_ARTEMIS_BROKER_URL=tcp://localhost:61616 \
ARTEMIS_PROD_USER=admin \
ARTEMIS_PROD_PASSWORD=admin \
./mvnw spring-boot:run -Dspring-boot.run.profiles=prod

This demonstrates: Env vars override profile YAML. This is how Kubernetes injects secrets — the YAML points to ${VARIABLE} and the orchestrator provides the value.

🧪 Experiment C: Check Active Profile at Runtime

Add this to your NotificationHubApplication.java to print the active profile on startup:

@SpringBootApplication
public class NotificationHubApplication {

    public static void main(String[] args) {
        ConfigurableApplicationContext ctx =
            SpringApplication.run(NotificationHubApplication.class, args);

        String[] profiles = ctx.getEnvironment().getActiveProfiles();
        System.out.println("🔧 Active profiles: " + String.join(", ", profiles));
    }
}

  SAME JAR DEPLOYED TO THREE ENVIRONMENTS
  ═══════════════════════════════════════════════════════════════════

  ┌─ Dev (your laptop) ──────────────────────────────────────────┐
  │  SPRING_PROFILES_ACTIVE=dev                                  │
  │  App ──tcp://localhost:61616──→ Docker Artemis               │
  │  Port: 8081  |  Logs: DEBUG  |  Creds: admin/admin           │

  ┌─ Staging (AWS / K8s) ───────────────────────────────────────┐
  │  SPRING_PROFILES_ACTIVE=staging                              │
  │  App ──tcp://broker.staging.internal:61616──→ Amazon MQ      │
  │  Port: 8080  |  Logs: INFO   |  Creds: from K8s secret      │

  ┌─ Production (AWS / K8s) ────────────────────────────────────┐
  │  SPRING_PROFILES_ACTIVE=prod                                 │
  │  App ──tcp://broker.prod.internal:61616──→ Amazon MQ cluster │
  │  Port: 8080  |  Logs: WARN   |  Creds: from Vault/K8s       │
  └──────────────────────────────────────────────────────────────┘

  ONE JAR. ZERO CODE CHANGES. THE PROFILE DECIDES EVERYTHING.
Interview Insight

"We build once, deploy everywhere. The JAR is immutable. Spring Profiles plus environment variables control which broker, which credentials, and which log level the application uses. In Kubernetes, the Deployment manifest injects SPRING_PROFILES_ACTIVE as an env var, and secrets come from ConfigMaps or Vault."

Knowledge Check

When you activate the dev profile, which files does Spring Boot load?

  • Both application.yml (base) AND application-dev.yml (profile), with profile values winning on conflicts
  • Only application-dev.yml — the base application.yml is completely ignored when any profile is active
  • Only application.yml — profile files are only loaded if explicitly imported with spring.config.import
  • All files: application.yml, application-dev.yml, application-prod.yml, and application-test.yml together

Your application-prod.yml uses ${ARTEMIS_PROD_PASSWORD}. What does this syntax do?

  • Resolves to an environment variable of that name at runtime — the value comes from the OS/container, never committed to Git
  • References a Spring bean named ARTEMIS_PROD_PASSWORD and calls its toString() method to get the password value
  • Looks up the value from a centralized Spring Cloud Config Server that must be running on a separate port
  • Generates a random password at startup and stores it in a file named ARTEMIS_PROD_PASSWORD for later reference

You run: SPRING_ARTEMIS_BROKER_URL=tcp://custom:61616 java -jar app.jar --spring.profiles.active=dev. Your application-dev.yml says broker-url: tcp://localhost:61616. Which broker does the app connect to?

  • tcp://custom:61616 — environment variables override profile-specific YAML properties in the priority order
  • tcp://localhost:61616 — profile-specific YAML always takes the highest priority over any other source
  • The application fails to start because of a conflict between the two different broker URL values
  • It depends on which was defined first — Spring Boot uses a first-defined-wins strategy for properties

What does spring.artemis.mode=embedded do differently from native?

  • Starts an Artemis broker inside the application's own JVM process — no external broker needed, ideal for testing
  • Connects to a broker that's running on the same machine but uses shared memory instead of TCP sockets
  • Downloads and installs Artemis locally, then connects to it via TCP on the default port automatically
  • Uses Spring Boot's built-in message queue implementation instead of the real ActiveMQ Artemis engine
