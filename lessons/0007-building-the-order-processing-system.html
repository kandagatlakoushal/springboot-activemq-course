Building the Order Processing System

Project 2 — a multi-service event-driven architecture using queues and topics together

📅 Lesson 07 of 14 ⏱ 60 min (read + build) 🎯 Project 2: Order Processing System (new project)

What You'll Build

This is the second major project in your learning path. You will build an Order Processing System that demonstrates real enterprise event-driven architecture — the exact pattern used at financial companies like S&P Global MI for processing trade orders, credit ratings, and market data updates.

  • A REST API that accepts new orders
  • An Order Placement Queue (point-to-point) for reliable order processing
  • An Order Events Topic (pub/sub) that broadcasts events to independent services
  • Three downstream services: Inventory, Payment, and Notification
  • Each service reacts independently — adding or removing a service requires ZERO code changes in the Order Service
Why This Architecture Matters

This project combines everything from Lessons 01–06: Spring Boot setup, broker connection, Spring Profiles, JSON message conversion, queues, and topics — into one coherent system. An interviewer at S&P Global MI will expect you to diagram and explain this exact pattern.

Why Both Queue AND Topic?

Destination Type Purpose Consumer
order.process.queue Queue Reliable order processing — must be handled exactly once OrderProcessor (single consumer)
order.events Topic Broadcast "order placed" event to any interested service Inventory + Payment + Notification (all get it)
Interview Insight

"We use a queue for the command ('process this order' — must happen once, reliably) and a topic for the event ('an order was placed' — whoever cares can subscribe). The order processor is the queue consumer. Downstream services like inventory, payment, and notifications subscribe to the topic independently. Adding a new subscriber (e.g., analytics) requires zero changes to the order service."

// Model/OrderRequest.java — what the HTTP client sends
package com.learningPath.OrderProcessingSystem.Model;

public class OrderRequest {

    private String customerId;
    private String productName;
    private int quantity;
    private double pricePerUnit;

    // Default constructor (required for Jackson HTTP deserialization)
    public OrderRequest() {}

    // Getters and Setters
    public String getCustomerId() { return customerId; }
    public void setCustomerId(String customerId) { this.customerId = customerId; }

    public String getProductName() { return productName; }
    public void setProductName(String productName) { this.productName = productName; }

    public int getQuantity() { return quantity; }
    public void setQuantity(int quantity) { this.quantity = quantity; }

    public double getPricePerUnit() { return pricePerUnit; }
    public void setPricePerUnit(double pricePerUnit) { this.pricePerUnit = pricePerUnit; }
}
// Model/OrderEvent.java — what travels through JMS
package com.learningPath.OrderProcessingSystem.Model;

import java.time.LocalDateTime;

public class OrderEvent {

    private String orderId;
    private String customerId;
    private String productName;
    private int quantity;
    private double totalAmount;
    private String status;
    private String timestamp;

    // Default constructor (required for Jackson JMS deserialization)
    public OrderEvent() {}

    public OrderEvent(String orderId, String customerId, String productName,
                      int quantity, double totalAmount, String status) {
        this.orderId = orderId;
        this.customerId = customerId;
        this.productName = productName;
        this.quantity = quantity;
        this.totalAmount = totalAmount;
        this.status = status;
        this.timestamp = LocalDateTime.now().toString();
    }

    // --- Getters and Setters ---
    public String getOrderId() { return orderId; }
    public void setOrderId(String orderId) { this.orderId = orderId; }

    public String getCustomerId() { return customerId; }
    public void setCustomerId(String customerId) { this.customerId = customerId; }

    public String getProductName() { return productName; }
    public void setProductName(String productName) { this.productName = productName; }

    public int getQuantity() { return quantity; }
    public void setQuantity(int quantity) { this.quantity = quantity; }

    public double getTotalAmount() { return totalAmount; }
    public void setTotalAmount(double totalAmount) { this.totalAmount = totalAmount; }

    public String getStatus() { return status; }
    public void setStatus(String status) { this.status = status; }

    public String getTimestamp() { return timestamp; }
    public void setTimestamp(String timestamp) { this.timestamp = timestamp; }

    @Override
    public String toString() {
        return "OrderEvent{orderId='" + orderId + "', customer='" + customerId +
               "', product='" + productName + "', qty=" + quantity +
               ", total=$" + String.format("%.2f", totalAmount) + "}";
    }
}
Design Decision: Two Separate Models

We deliberately separate OrderRequest (HTTP input) from OrderEvent (JMS payload). In enterprise systems, the API contract and the internal event contract often differ — the event adds computed fields (like totalAmount, orderId, timestamp) that the client didn't provide. This is a standard pattern in Domain-Driven Design (DDD).

Step 5: JMS Configuration

// Config/JmsConfig.java
package com.learningPath.OrderProcessingSystem.Config;

import jakarta.jms.ConnectionFactory;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.jms.config.DefaultJmsListenerContainerFactory;
import org.springframework.jms.config.JmsListenerContainerFactory;
import org.springframework.jms.support.converter.JacksonJsonMessageConverter;
import org.springframework.jms.support.converter.MessageConverter;
import org.springframework.jms.support.converter.MessageType;

@Configuration
public class JmsConfig {

    @Bean
    public MessageConverter jacksonJmsMessageConverter() {
        JacksonJsonMessageConverter converter = new JacksonJsonMessageConverter();
        converter.setTargetType(MessageType.TEXT);
        converter.setTypeIdPropertyName("_type");
        return converter;
    }

    @Bean
    public JmsListenerContainerFactory<?> topicFactory(
            ConnectionFactory connectionFactory,
            MessageConverter messageConverter) {
        DefaultJmsListenerContainerFactory factory = new DefaultJmsListenerContainerFactory();
        factory.setConnectionFactory(connectionFactory);
        factory.setMessageConverter(messageConverter);
        factory.setPubSubDomain(true);
        return factory;
    }
}

Step 6: Order Producer

// Producer/OrderProducer.java
package com.learningPath.OrderProcessingSystem.Producer;

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.jms.core.JmsTemplate;
import org.springframework.stereotype.Service;
import com.learningPath.OrderProcessingSystem.Model.OrderEvent;

@Service
public class OrderProducer {

    private final Logger log = LoggerFactory.getLogger(this.getClass());
    private final JmsTemplate jmsTemplate;

    @Value("${app.queue.order-process}")
    private String orderQueue;

    @Value("${app.topic.order-events}")
    private String orderTopic;

    public OrderProducer(JmsTemplate jmsTemplate) {
        this.jmsTemplate = jmsTemplate;
    }

    public void placeOrder(OrderEvent event) {
        // 1. Send command to queue (reliable, exactly-once processing)
        log.info("📦 [QUEUE] Sending order {} to processing queue", event.getOrderId());
        jmsTemplate.convertAndSend(orderQueue, event);

        // 2. Broadcast event to topic (fan-out to all subscribers)
        log.info("📢 [TOPIC] Broadcasting order {} event to all subscribers", event.getOrderId());
        jmsTemplate.setPubSubDomain(true);
        jmsTemplate.convertAndSend(orderTopic, event);
        jmsTemplate.setPubSubDomain(false);
    }
}

Step 7: Order Controller (REST API)

// Controller/OrderController.java
package com.learningPath.OrderProcessingSystem.Controller;

import java.util.UUID;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.*;
import com.learningPath.OrderProcessingSystem.Model.OrderRequest;
import com.learningPath.OrderProcessingSystem.Model.OrderEvent;
import com.learningPath.OrderProcessingSystem.Producer.OrderProducer;

@RestController
@RequestMapping("/api/orders")
public class OrderController {

    private final Logger log = LoggerFactory.getLogger(this.getClass());
    private final OrderProducer producer;

    public OrderController(OrderProducer producer) {
        this.producer = producer;
    }

    @PostMapping
    public ResponseEntity<OrderEvent> createOrder(@RequestBody OrderRequest request) {
        log.info("🛒 Received order from customer: {}", request.getCustomerId());

        // Transform HTTP request into a domain event
        String orderId = "ORD-" + UUID.randomUUID().toString().substring(0, 8).toUpperCase();
        double total = request.getQuantity() * request.getPricePerUnit();

        OrderEvent event = new OrderEvent(
            orderId,
            request.getCustomerId(),
            request.getProductName(),
            request.getQuantity(),
            total,
            "PLACED"
        );

        producer.placeOrder(event);

        return ResponseEntity.ok(event);
    }
}

Step 8: Queue Consumer — Order Processor

// Consumer/OrderProcessor.java
package com.learningPath.OrderProcessingSystem.Consumer;

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.jms.annotation.JmsListener;
import org.springframework.stereotype.Service;
import com.learningPath.OrderProcessingSystem.Model.OrderEvent;

@Service
public class OrderProcessor {

    private final Logger log = LoggerFactory.getLogger(this.getClass());

    @JmsListener(destination = "${app.queue.order-process}")
    public void processOrder(OrderEvent event) {
        log.info("⚙️  [ORDER PROCESSOR] Processing order {}", event.getOrderId());
        log.info("   ├─ Customer:  {}", event.getCustomerId());
        log.info("   ├─ Product:   {} × {}", event.getProductName(), event.getQuantity());
        log.info("   ├─ Total:     ${}", String.format("%.2f", event.getTotalAmount()));
        log.info("   └─ Status:    PROCESSING → CONFIRMED");

        // Simulate processing delay
        try { Thread.sleep(500); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }

        log.info("✅ [ORDER PROCESSOR] Order {} confirmed!", event.getOrderId());
    }
}

Knowledge Check

Why does the Order Processing System use BOTH a queue AND a topic for the same order event?

  • The queue guarantees exactly-once processing (command: 'process this order'), while the topic broadcasts the event to all interested services (event: 'order was placed')
  • Using both is required by the JMS specification when sending messages larger than 1KB in size
  • The queue is for internal services and the topic is exclusively for external third-party consumers
  • Spring Boot requires both a queue and topic for the JacksonJsonMessageConverter to work correctly

You want to add a fifth microservice (FraudDetectionService) that also needs to know about every order placed. What do you change?

  • Create a new FraudDetectionSubscriber class with @JmsListener on the same topic. No changes to the producer, controller, or other subscribers.
  • Modify the OrderProducer to add a fifth convertAndSend() call specifically for the fraud detection queue
  • Update the OrderController to accept a list of subscriber URLs and POST to each one directly via HTTP
  • Add a new queue for fraud detection and modify the JmsConfig to route messages to both the topic and this new queue

Why do we separate OrderRequest (HTTP model) from OrderEvent (JMS model)?

  • Because the API input and the internal event have different shapes — the event includes computed fields (orderId, totalAmount, timestamp) that the client didn't send
  • Because Spring Boot cannot serialize the same class for both HTTP/JSON and JMS/JSON at the same time
  • Because the JMS specification forbids reusing the same Java class across REST and messaging boundaries
  • There's no real reason — it's just a convention. Using one class would work identically and be simpler
