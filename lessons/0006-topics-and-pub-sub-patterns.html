Part 1: Queues vs Topics — The Infrastructure Model

Queue: Point-to-Point (What You Built So Far)

In Lessons 03–05, you used a Queue. In queue-based messaging, each message is consumed by exactly one consumer. If three instances of your app are listening on the same queue, the broker load-balances — each message goes to only one of them.


  QUEUE: POINT-TO-POINT (Competing Consumers)
  ════════════════════════════════════════════

  Producer ──→ [ notification.queue ] ──→ Consumer A  ✓ gets msg 1
                                     ──→ Consumer B  ✓ gets msg 2
                                     ──→ Consumer C  ✓ gets msg 3

  Each message delivered to EXACTLY ONE consumer.
  The broker round-robins across consumers.
  Use case: Work distribution, task processing, order fulfillment.

Topic: Publish-Subscribe (What We're Building Now)

A Topic is fundamentally different. Every message published to a topic is delivered to ALL active subscribers. Each subscriber gets its own independent copy.


  TOPIC: PUBLISH-SUBSCRIBE (Fan-Out / Broadcast)
  ═══════════════════════════════════════════════

                                     ┌──→ Email Service     ✓ gets EVERY message
  Producer ──→ [ order.events ] ─────┼──→ SMS Service       ✓ gets EVERY message
                                     ├──→ Audit Logger      ✓ gets EVERY message
                                     └──→ Analytics Engine  ✓ gets EVERY message

  Each message delivered to ALL subscribers simultaneously.
  Subscribers are independent — they don't know about each other.
  Use case: Event notification, audit logging, real-time analytics.

When to Use Which?

Criteria Queue (Point-to-Point) Topic (Pub/Sub)
Delivery One consumer per message All subscribers get every message
Consumer Coupling Consumers compete for messages Consumers are completely independent
Use Case Task distribution (process this order) Event broadcasting (an order was placed)
If No Consumer Active Messages wait in the queue Messages are lost! (unless durable subscriber)
S&P Example Process credit rating calculation Broadcast "new rating published" event
Interview Insight

"In event-driven architectures, we use Queues for commands (do this work) and Topics for events (this thing happened). A queue says 'process this order.' A topic says 'an order was placed' — and whoever cares can listen. The producer doesn't know or care how many consumers exist."

Part 2: The Infrastructure Detail — How Topics Work at the Broker


  WHAT HAPPENS INSIDE ARTEMIS WHEN YOU PUBLISH TO A TOPIC
  ═══════════════════════════════════════════════════════════

  1. Producer sends message to address "notification.events" (topic)
         │
         ▼
  2. Artemis looks up all ACTIVE SUBSCRIPTIONS on this address
         │
         ├──→ Subscription 1: EmailService  (connected via TCP)
         ├──→ Subscription 2: SmsService    (connected via TCP)
         └──→ Subscription 3: AuditLogger   (connected via TCP)
         │
         ▼
  3. Artemis creates a COPY of the message for each subscription
     and delivers independently to each consumer thread

  ⚠️ KEY DIFFERENCE FROM QUEUES:
     - Queue: Broker has ONE copy, delivers to ONE consumer
     - Topic: Broker creates N copies for N subscribers
     - Topic: If NO subscribers are active, the message is DISCARDED
       (unless using Durable Subscriptions — covered in Lesson 12)
Infrastructure Detail: Artemis Addressing Model

Artemis uses an address model that unifies queues and topics under a single abstraction:

  • An address is a named routing endpoint (like notification.events)
  • A multicast address behaves as a Topic — messages go to all bound queues
  • An anycast address behaves as a Queue — messages go to one bound queue

When Spring sets pubSubDomain=true, it tells Artemis to treat the destination as a multicast address.

Part 3: The pubSubDomain Problem

Here's the critical gotcha that trips up every beginner: Spring Boot's auto-configured JmsListenerContainerFactory defaults to queue mode (pubSubDomain = false). If you use @JmsListener on a topic destination without setting this flag, the listener will behave as a queue consumer — only one instance gets each message!

The fix is to create a separate factory bean for topic listeners:


  TWO FACTORIES, TWO MODES
  ════════════════════════

  Default Factory (auto-configured)
  ├── pubSubDomain = false (queue mode)
  └── Used by: @JmsListener(destination = "notification.queue")

  Custom "topicFactory" Bean (you create this)
  ├── pubSubDomain = true (topic mode)
  └── Used by: @JmsListener(destination = "notification.events",
                             containerFactory = "topicFactory")

Part 4: Build It — Upgrade Your Notification Hub

We will add topic-based broadcasting to your existing project. When a notification is sent, it now goes to BOTH a queue (for processing) AND a topic (for broadcasting to Email, SMS, and Audit services).

Step 1: Update application.yml (Base Config)

Add the topic destination name to your shared base config:

# src/main/resources/application.yml — add topic destination
spring:
  application:
    name: NotificationHub
  profiles:
    active: dev

app:
  queue:
    notification: notification.queue     # existing queue (point-to-point)
  topic:
    notification: notification.events    # NEW topic (pub/sub broadcast)

Step 2: Update JmsConfig — Add the Topic Factory

Add a second factory bean to your existing JmsConfig.java:

// src/main/java/.../Config/JmsConfig.java
package com.learningPath.springProfileAmq.NotificationHub.Config;

import jakarta.jms.ConnectionFactory;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.jms.config.DefaultJmsListenerContainerFactory;
import org.springframework.jms.config.JmsListenerContainerFactory;
import org.springframework.jms.support.converter.MappingJackson2MessageConverter;
import org.springframework.jms.support.converter.MessageConverter;
import org.springframework.jms.support.converter.MessageType;

@Configuration
public class JmsConfig {

    // Existing bean from Lesson 05 — JSON message conversion
    @Bean
    public MessageConverter jacksonJmsMessageConverter() {
        MappingJackson2MessageConverter converter = new MappingJackson2MessageConverter();
        converter.setTargetType(MessageType.TEXT);
        converter.setTypeIdPropertyName("_type");
        return converter;
    }

    // NEW — Factory for Topic (pub/sub) listeners
    @Bean
    public JmsListenerContainerFactory<?> topicFactory(
            ConnectionFactory connectionFactory,
            MessageConverter messageConverter) {

        DefaultJmsListenerContainerFactory factory = new DefaultJmsListenerContainerFactory();
        factory.setConnectionFactory(connectionFactory);     // same Artemis connection
        factory.setMessageConverter(messageConverter);        // reuse our Jackson converter
        factory.setPubSubDomain(true);                        // ← THE CRITICAL FLAG!
        return factory;
    }
}
The Most Common Mistake

If you forget factory.setPubSubDomain(true), your @JmsListener will subscribe to a queue named notification.events instead of a topic. Only one consumer will receive each message. You'll spend hours debugging why your Email and SMS services aren't both getting the same event.

Step 3: Update NotificationSender — Publish to the Topic

Add a topic publishing method alongside your existing queue send:

// src/main/java/.../Service/NotificationSender.java
package com.learningPath.springProfileAmq.NotificationHub.Service;

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.jms.core.JmsTemplate;
import org.springframework.stereotype.Service;
import com.learningPath.springProfileAmq.NotificationHub.Model.NotificationMessage;

@Service
public class NotificationSender {

    private final Logger log = LoggerFactory.getLogger(this.getClass());
    private final JmsTemplate jmsTemplate;

    @Value("${app.queue.notification}")
    private String queueName;

    @Value("${app.topic.notification}")
    private String topicName;

    public NotificationSender(JmsTemplate jmsTemplate) {
        this.jmsTemplate = jmsTemplate;
    }

    // Existing — send to queue (point-to-point processing)
    public void sendToQueue(NotificationMessage message) {
        log.info("📤 [QUEUE] Sending to [{}]: {}", queueName, message);
        jmsTemplate.convertAndSend(queueName, message);
    }

    // NEW — publish to topic (broadcast to all subscribers)
    public void publishToTopic(NotificationMessage message) {
        log.info("📢 [TOPIC] Broadcasting to [{}]: {}", topicName, message);
        jmsTemplate.setPubSubDomain(true);   // switch to topic mode for this send
        jmsTemplate.convertAndSend(topicName, message);
        jmsTemplate.setPubSubDomain(false);  // reset back to queue mode
    }
}
Infrastructure Detail: Why Toggle pubSubDomain?

The JmsTemplate bean is shared across your entire application. By default it's in queue mode (pubSubDomain=false). When you want to send to a topic, you temporarily flip the flag. In production, a cleaner approach is to create two separate JmsTemplate beans — one for queues, one for topics. We keep it simple here to focus on the concept.

Step 4: Create Topic Subscribers

Create three independent subscriber services. Each simulates a different downstream system:

// src/main/java/.../Service/EmailSubscriber.java
package com.learningPath.springProfileAmq.NotificationHub.Service;

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.jms.annotation.JmsListener;
import org.springframework.stereotype.Service;
import com.learningPath.springProfileAmq.NotificationHub.Model.NotificationMessage;

@Service
public class EmailSubscriber {

    private final Logger log = LoggerFactory.getLogger(this.getClass());

    @JmsListener(destination = "${app.topic.notification}",
                 containerFactory = "topicFactory")    // ← uses our pub/sub factory!
    public void onNotification(NotificationMessage msg) {
        log.info("📧 [EMAIL] Sending email to {}: {}", msg.getRecipient(), msg.getContent());
    }
}
// src/main/java/.../Service/SmsSubscriber.java
package com.learningPath.springProfileAmq.NotificationHub.Service;

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.jms.annotation.JmsListener;
import org.springframework.stereotype.Service;
import com.learningPath.springProfileAmq.NotificationHub.Model.NotificationMessage;

@Service
public class SmsSubscriber {

    private final Logger log = LoggerFactory.getLogger(this.getClass());

    @JmsListener(destination = "${app.topic.notification}",
                 containerFactory = "topicFactory")
    public void onNotification(NotificationMessage msg) {
        log.info("📱 [SMS] Sending SMS to {}: {}", msg.getRecipient(), msg.getContent());
    }
}
// src/main/java/.../Service/AuditSubscriber.java
package com.learningPath.springProfileAmq.NotificationHub.Service;

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.jms.annotation.JmsListener;
import org.springframework.stereotype.Service;
import com.learningPath.springProfileAmq.NotificationHub.Model.NotificationMessage;

@Service
public class AuditSubscriber {

    private final Logger log = LoggerFactory.getLogger(this.getClass());

    @JmsListener(destination = "${app.topic.notification}",
                 containerFactory = "topicFactory")
    public void onNotification(NotificationMessage msg) {
        log.info("📋 [AUDIT] Logged notification {} for {} at {}", 
                 msg.getId(), msg.getRecipient(), msg.getTimestamp());
    }
}

Notice the key difference from your queue listener: each subscriber specifies containerFactory = "topicFactory". This tells Spring to use the pub/sub factory we created.

Step 5: Update NotificationController

Add a new endpoint that publishes to the topic, alongside your existing queue endpoint:

// src/main/java/.../Controller/NotificationController.java
package com.learningPath.springProfileAmq.NotificationHub.Controller;

import java.util.UUID;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.*;
import com.learningPath.springProfileAmq.NotificationHub.Model.NotificationMessage;
import com.learningPath.springProfileAmq.NotificationHub.Service.NotificationSender;

@RestController
@RequestMapping("/app")
public class NotificationController {

    private final Logger log = LoggerFactory.getLogger(this.getClass());
    private final NotificationSender sender;

    public NotificationController(NotificationSender sender) {
        this.sender = sender;
    }

    // Existing queue endpoint (from Lesson 05)
    @PostMapping("/notify")
    public ResponseEntity<NotificationMessage> notify(
            @RequestParam String recipient, 
            @RequestParam String content) {

        String alertId = "ALT-" + UUID.randomUUID().toString().substring(0, 8).toUpperCase();
        NotificationMessage msg = new NotificationMessage(alertId, recipient, content, "DISPATCHED");
        sender.sendToQueue(msg);
        return ResponseEntity.ok(msg);
    }

    // NEW — broadcast to all subscribers via topic
    @PostMapping("/broadcast")
    public ResponseEntity<NotificationMessage> broadcast(
            @RequestParam String recipient,
            @RequestParam String content) {

        String alertId = "BRC-" + UUID.randomUUID().toString().substring(0, 8).toUpperCase();
        NotificationMessage msg = new NotificationMessage(alertId, recipient, content, "BROADCAST");
        sender.publishToTopic(msg);
        return ResponseEntity.ok(msg);
    }
}

Part 6: Experiments (Desirable Difficulty)

🧪 Experiment A: Remove One Subscriber — Others Still Work

  1. Comment out the @Service annotation on SmsSubscriber.java
  2. Restart the app and send a broadcast
  3. Notice: Email and Audit still receive the message — SMS is simply gone
  4. This proves: Subscribers are fully independent. Adding or removing one has ZERO impact on others. This is the power of event-driven decoupling.

🧪 Experiment B: Forget the containerFactory — Watch It Break

  1. In EmailSubscriber.java, remove containerFactory = "topicFactory" from the @JmsListener annotation
  2. Restart and send a broadcast. Only ONE of your three subscribers gets each message (random round-robin)
  3. Put it back and restart — all three get every message again
  4. This proves: Without containerFactory = "topicFactory", Spring treats the destination as a queue, not a topic

🧪 Experiment C: Stop the App, Send a Message, Restart

  1. Stop the Notification Hub application
  2. Use the Artemis Web Console (port 8161) to manually send a message to the topic notification.events
  3. Restart the application
  4. Did your subscribers receive the message? No! Topic messages are only delivered to active subscribers
  5. Now try the same with the queue notification.queue — the queue message IS delivered after restart!
  6. This proves: Topics require active subscribers. Queues persist messages. (Durable subscriptions fix this — Lesson 12)

Knowledge Check

You publish one message to a Topic with 5 active subscribers. How many copies of the message are delivered?

  • 5 — every active subscriber receives its own copy of the message independently
  • 1 — the broker round-robins and only one subscriber gets each message
  • It depends on the broker load — Artemis decides based on memory pressure
  • 0 — topics only store messages, subscribers must manually poll for them

What happens if you publish to a Topic and NO subscribers are currently active?

  • The message is discarded — topics only deliver to active subscribers (unless using durable subscriptions)
  • The broker stores the message indefinitely until a subscriber eventually connects and consumes it
  • The message is automatically redirected to a fallback queue named "undelivered"
  • Artemis throws a NoSubscriberException and the producer's convertAndSend() call fails

Why do topic @JmsListener methods need containerFactory = "topicFactory"?

  • Because the default factory uses queue mode (pubSubDomain=false). The topicFactory sets pubSubDomain=true to enable pub/sub behavior
  • Because topic listeners require a different TCP port and the topicFactory configures port 61617
  • Because Spring Boot cannot auto-detect whether a destination name refers to a queue or topic
  • Because topics use a different serialization format than queues and need a separate MessageConverter

In enterprise architecture, when do you choose a Queue vs a Topic?

  • Queue for commands (one consumer processes the task); Topic for events (multiple services react to something that happened)
  • Queue for fast messages; Topic for slow messages that need more processing time
  • Queue for small payloads under 1KB; Topic for large payloads over 1KB
  • Queue for internal services; Topic for external third-party integrations only

Your Checkpoint

  • ✅ Explain Queue (point-to-point, competing consumers) vs Topic (pub/sub, fan-out broadcast)
  • ✅ Configure a dedicated topicFactory with pubSubDomain=true
  • ✅ Build multiple independent subscribers that each receive every message
  • ✅ Know that topic messages are lost without active subscribers (vs queues which persist)
  • ✅ Articulate the "Queues for commands, Topics for events" design principle
