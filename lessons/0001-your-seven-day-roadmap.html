The Big Picture

You already know Spring Boot — REST controllers, services, JPA repositories. That's your foundation. Over the next 7 days, you'll add two powerful capabilities on top of it:

  1. Spring Profiles — switching between dev/test/prod configurations without changing code
  2. ActiveMQ Messaging — decoupling services through asynchronous message queues and topics

You'll learn these by building three progressively complex projects, each one teaching new concepts while reinforcing the ones before.

But first — let's make sure you understand where all of this lives and how it actually works at the infrastructure level.

Infrastructure Foundations

Before we write a single line of Spring Boot code, you need a clear mental picture of what's physically happening when services communicate through a message broker. This is interview gold — many candidates can write @JmsListener but can't explain what's happening on the wire.

What is a Service?

A service is just a running Java process — your Spring Boot application packaged as a JAR, executing on a server. That server could be:

  • Your laptop (during development)
  • A bare-metal server in a data center
  • A virtual machine (EC2 instance on AWS)
  • A Docker container running on Kubernetes

Each service listens on a port (e.g., your REST API on port 8080). Other systems talk to it by knowing its host + port — like order-service.prod.internal:8080.

The Problem: Tight Coupling

Imagine you have an Order Service that, after creating an order, needs to:

  1. Tell the Inventory Service to reserve stock
  2. Tell the Email Service to send a confirmation
  3. Tell the Analytics Service to log the event

With REST calls, your Order Service looks like this:


  ┌──────────────┐     HTTP POST      ┌───────────────────┐
  │              │───────────────────→ │ Inventory Service │
  │              │     HTTP POST      │   :8081            │
  │ Order        │───────────────────→ ├───────────────────┤
  │ Service      │                    │ Email Service     │
  │ :8080        │     HTTP POST      │   :8082            │
  │              │───────────────────→ ├───────────────────┤
  │              │                    │ Analytics Service │
  └──────────────┘                    │   :8083            │
                                      └───────────────────┘

This is tightly coupled. The Order Service must:

  • Know the address of every downstream service (host + port)
  • Wait for each HTTP response before proceeding
  • Handle failures — what if Email Service is down? Does the order fail?
  • Change its code every time a new consumer is added
Interview Insight

If an interviewer asks "why not just use REST calls between services?" — this is your answer. REST creates a temporal coupling (caller waits for response) and a knowledge coupling (caller must know who to call). Both are fragile at scale.

The Solution: A Message Broker

A message broker is a dedicated server process — like a post office — that sits between your services. It's a separate running application (ActiveMQ Artemis, in our case) deployed on its own host and port.


  ┌──────────────┐                    ┌───────────────────┐
  │              │    TCP :61616      │                   │
  │ Order        │───────────────────→│   ActiveMQ        │
  │ Service      │   "Here's an      │   Artemis         │
  │ :8080        │    order event"    │   (The Broker)    │
  │              │                    │                   │
  └──────────────┘                    │  Stores messages  │
                                      │  in queues/topics │
  The Order Service is DONE.          │                   │
  It doesn't wait. It doesn't        │                   │
  know who will read the message.     └──────┬──┬──┬──────┘
                                             │  │  │
                              ┌──────────────┘  │  └──────────────┐
                              │                 │                 │
                              ▼                 ▼                 ▼
                    ┌─────────────┐   ┌─────────────┐   ┌─────────────┐
                    │ Inventory   │   │ Email       │   │ Analytics   │
                    │ Service     │   │ Service     │   │ Service     │
                    │ :8081       │   │ :8082       │   │ :8083       │
                    └─────────────┘   └─────────────┘   └─────────────┘

                    Each consumer connects to the broker independently.
                    They pull messages at their own pace.

Now the Order Service is decoupled:

  • It only knows the broker's address (tcp://broker:61616) — not the consumers
  • It sends the message and returns immediately — no waiting
  • If Email Service is down, the message waits in the broker until it comes back
  • Adding a new consumer (e.g., Fraud Detection) requires zero changes to Order Service

Where Does the Broker Run?

The broker is just another process, deployed like any other service:

Environment How the Broker Runs Broker URL
Local Dev Docker container on your laptop, or embedded inside your Spring Boot app (same JVM) tcp://localhost:61616
Test/QA Dedicated VM or container in a test cluster tcp://artemis.test.internal:61616
Production Clustered brokers (multiple instances for high availability), often behind a load balancer or managed service (e.g., Amazon MQ) tcp://artemis.prod.internal:61616
Key Ports to Know
  • 61616 — The JMS/OpenWire protocol port. Your Spring Boot app connects here via TCP.
  • 8161 — The broker's web management console (like a dashboard to see queues, messages, consumers).
  • 5672 — AMQP protocol port (used by non-Java clients, RabbitMQ-style).

How Do Services Actually Talk to the Broker?

Under the hood, the communication is simple:

  1. TCP Connection — Your Spring Boot app opens a persistent TCP socket to the broker on port 61616. This is what ConnectionFactory manages.
  2. Protocol — Over that TCP connection, they speak a messaging protocol (OpenWire for JMS, or AMQP/STOMP/MQTT). Spring Boot + Artemis uses CORE protocol by default.
  3. Send — The producer serializes a message (text, JSON bytes, etc.) and sends it to a named destination (e.g., order.queue). The broker stores it.
  4. Receive — The consumer has a listener thread that receives messages from the broker as they arrive (push model via @JmsListener), or pulls them on demand.
Think of It Like This

REST = phone call (synchronous, both parties must be available, caller waits for answer)
Messaging = postal mail (asynchronous, sender drops it off, recipient picks it up whenever they're ready, post office stores it in between)

What Happens When a Service Goes Down?

This is where messaging shines vs. REST:

Scenario With REST With Messaging
Consumer is down ❌ HTTP 503 error. Producer must retry or fail. ✅ Messages queue up in the broker. Consumer processes them when it's back.
Consumer is slow ❌ Producer's thread blocks, timeouts, cascading failures. ✅ Messages buffer. Consumer works at its own pace.
New consumer added ❌ Producer must add a new HTTP call, redeploy. ✅ New consumer subscribes to existing topic. Zero producer changes.
Broker is down N/A ❌ Nobody can send or receive. This is why production uses clustered brokers.

The Three Projects

🏗️ Project 1: Notification Hub Days 1–2

A single Spring Boot app that sends and receives notifications via ActiveMQ. Your "Hello World" of messaging — but with real structure.

You'll learn:

  • Setting up ActiveMQ Artemis (Docker or embedded)
  • JMS fundamentals — ConnectionFactory, JmsTemplate, @JmsListener
  • Queues (point-to-point): one producer, one consumer
  • Spring Profiles: application-dev.yml vs application-prod.yml
  • Sending plain text and JSON messages

🛒 Project 2: Order Processing System Days 3–5

A multi-module system where an Order Service publishes events and multiple downstream services consume them. This is the heart of enterprise messaging.

You'll learn:

  • Topics (pub/sub): one producer, many consumers
  • Message converters — auto-serializing POJOs to JSON
  • Message selectors and filtering
  • Dead Letter Queues (DLQ) — handling poison messages
  • Spring Profiles with @Profile beans — swapping implementations per environment
  • Profile groups — activating related profiles together
  • Request-Reply pattern with JmsTemplate.sendAndReceive()

🏦 Project 3: Financial Data Pipeline Days 6–7

An enterprise-grade pipeline that ingests market data, processes it through a chain of services, and publishes enriched results. Designed to mirror patterns you'd see at S&P Global MI.

You'll learn:

  • Durable subscribers — surviving broker restarts
  • Transactions — ensuring message + database consistency
  • Connection pooling with CachingConnectionFactory
  • Message priority, TTL, and delivery modes
  • Integration testing messaging with @EmbeddedActiveMQ
  • ActiveMQ Classic vs Artemis — interview-ready comparison
  • Production configuration with Spring Profiles

Quick Knowledge Check

In enterprise messaging, what does "decoupling" mean?

  • Services communicate through a broker without knowing about each other directly
  • Services share the same database to exchange information between each other
  • Services call each other's REST APIs but with retry logic added on top
  • Services are deployed on separate servers but call each other synchronously

Which Spring Boot 3 starter provides ActiveMQ Artemis support?

  • spring-boot-starter-artemis
  • spring-boot-starter-activemq
  • spring-boot-starter-messaging
  • spring-boot-starter-jms-amq

What is the purpose of Spring Profiles?

  • Segregate configuration so different environments load different settings at runtime
  • Define user roles and permissions for your Spring Security configuration
  • Profile application performance and generate optimization reports automatically
  • Create different Maven build profiles for compilation and packaging steps
