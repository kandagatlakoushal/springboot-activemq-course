Part 1: The JMS Mental Model

JMS is a Spec, Not a Product

This is the first thing interviewers test. JMS (Java Message Service) is a specification — a set of Java interfaces that define how messaging should work. It's like JDBC:

Analogy Specification Implementation
Databases JDBC (the API) MySQL Driver, PostgreSQL Driver, Oracle Driver
Messaging JMS (the API) ActiveMQ Artemis, ActiveMQ Classic, IBM MQ, RabbitMQ*

*RabbitMQ supports JMS via a plugin, but natively uses AMQP.

You write your code against the JMS interfaces. The broker (Artemis) provides the implementation classes. If your company switches from Artemis to IBM MQ tomorrow, your code stays the same — only the driver (dependency + config) changes.

Interview Insight

"JMS is a specification (JSR 343 / Jakarta Messaging 3.1), not a product. ActiveMQ Artemis is one implementation. The key benefit is vendor portability — my @JmsListener code works with any JMS-compliant broker."

The 6 Core JMS Objects

JMS defines a hierarchy of objects. Understanding this hierarchy is essential because Spring Boot auto-configures most of them — but when something breaks, you need to know what's underneath.

Let's walk through each:

1. ConnectionFactory

What it is: A factory object that knows how to connect to the broker — the URL (tcp://localhost:61616), username, password.

Where it lives: In your application's memory. Spring Boot auto-creates it from your application.yml properties.

Infrastructure view: Think of it as a "contact card" for the broker. It doesn't open a connection when created — it just holds the information needed to open one later.

Thread-safe? Yes. One instance shared across your whole application.

2. Connection

What it is: An open TCP socket between your app and the broker.

Where it lives: Your app holds one end, the broker holds the other. It's a real network connection — if you run netstat on your machine, you'll see it.

Infrastructure view: This is the actual wire. When the connection opens, your app authenticates with the broker (user/password) and establishes a session protocol. If the network drops, this connection breaks.

Thread-safe? Yes, but expensive to create. Production apps pool or cache them.

3. Session

What it is: A single-threaded context for producing/consuming messages. Also handles transactions and acknowledgments.

Where it lives: Inside your application, associated with a Connection.

Infrastructure view: One Connection can have multiple Sessions — like multiple conversations over a single phone line. Each Session is a logical channel multiplexed over the TCP connection.

Thread-safe? No! Each thread must use its own Session. This is a common interview question.

4. MessageProducer

What it is: Sends messages to a Destination (queue or topic).

Where it lives: Created by a Session, bound to a specific destination.

Infrastructure view: When you call producer.send(message), the message is serialized to bytes, sent over the TCP connection to the broker, and the broker writes it to the destination's internal storage.

5. MessageConsumer

What it is: Receives messages from a Destination.

Where it lives: Created by a Session, attached to a specific destination.

Infrastructure view: The consumer registers with the broker. The broker then pushes messages to the consumer over the TCP connection. This is why @JmsListener works without polling — the broker initiates the delivery.

6. Destination

What it is: A named endpoint — either a Queue or a Topic. Just a name string like "order.queue".

Where it lives: On the broker. The broker creates the destination when the first message is sent (auto-create) or through configuration. Messages are stored here until consumed.

Infrastructure view: On the broker's filesystem, each destination has storage. In Artemis, this is a journal (append-only log files) stored at /var/lib/artemis-instance/data/journal/ inside the Docker container.

The Raw JMS Code (What You'll Never Write)

In raw JMS, sending a message takes ~15 lines of boilerplate. This is what Spring Boot saves you from:

// RAW JMS — you'll never write this, but you need to know what's happening

// 1. Create a factory (knows broker address)
ConnectionFactory factory = new ActiveMQConnectionFactory("tcp://localhost:61616");

// 2. Open a TCP connection to the broker
Connection connection = factory.createConnection("artemis", "artemis");
connection.start();

// 3. Create a session (single-threaded context)
Session session = connection.createSession(false, Session.AUTO_ACKNOWLEDGE);

// 4. Specify where to send (destination = queue name on the broker)
Destination destination = session.createQueue("order.queue");

// 5. Create a producer attached to that destination
MessageProducer producer = session.createProducer(destination);

// 6. Create and send the message
TextMessage message = session.createTextMessage("Order #001 placed");
producer.send(message);

// 7. Clean up (close everything in reverse order)
producer.close();
session.close();
connection.close();

The Spring Boot Code (What You'll Actually Write)

Spring Boot auto-configures the ConnectionFactory, manages Connections/Sessions behind the scenes, and gives you JmsTemplate — a one-liner wrapper:

// SPRING BOOT — this is all you write

@Service
public class OrderPublisher {

    private final JmsTemplate jmsTemplate;

    public OrderPublisher(JmsTemplate jmsTemplate) {
        this.jmsTemplate = jmsTemplate;  // Spring injects this automatically
    }

    public void placeOrder(String orderId) {
        jmsTemplate.convertAndSend("order.queue", "Order " + orderId + " placed");
        // That's it. ConnectionFactory → Connection → Session → Producer → send → cleanup
        // ALL handled by JmsTemplate internally.
    }
}
What Spring Boot Does For You
  • ConnectionFactory — Auto-created from spring.artemis.* properties in your YAML
  • JmsTemplate — Auto-created bean. Wraps the raw JMS API. Handles Connection/Session lifecycle.
  • @JmsListener — Creates a MessageConsumer in a background thread. Calls your method for each message.
  • Error conversion — JMS checked exceptions → Spring's unchecked exceptions
Interview Insight

"Under the hood, JmsTemplate opens a Connection, creates a Session, creates a MessageProducer, sends the message, then closes everything. In production, we wrap the ConnectionFactory with a CachingConnectionFactory to pool these objects instead of creating them fresh each time."

Step 1: Start Artemis in Docker

Open your terminal and run:

docker run -d --name artemis \
  -p 61616:61616 \
  -p 8161:8161 \
  -e ARTEMIS_USER=admin \
  -e ARTEMIS_PASSWORD=admin \
  apache/activemq-artemis:latest-alpine

Let's break down each flag:

Flag What It Does
-d Run in background (detached mode)
--name artemis Name the container "artemis" so you can reference it later
-p 61616:61616 Map host port 61616 to container port 61616 (JMS protocol)
-p 8161:8161 Map host port 8161 to container port 8161 (web console)
-e ARTEMIS_USER=admin Set the broker admin username
-e ARTEMIS_PASSWORD=admin Set the broker admin password
apache/activemq-artemis:latest-alpine Official Apache image (Alpine Linux for small size)

Step 2: Verify It's Running

# Check container status
docker ps

# Should show something like:
# CONTAINER ID   IMAGE                                    STATUS         PORTS
# a1b2c3d4e5f6   apache/activemq-artemis:latest-alpine   Up 30 seconds  0.0.0.0:61616->61616/tcp, 0.0.0.0:8161->8161/tcp

# Check broker logs (look for "Server is now live")
docker logs artemis
Troubleshooting

If port 61616 is already in use: docker stop artemis && docker rm artemis, then re-run the command.

If Docker isn't installed: Install Docker Desktop for Mac.

Step 3: Explore the Web Console

Open your browser and go to: http://localhost:8161

Login with admin / admin.

The web console is the broker's dashboard. Here's what you'll see and what it means:

Console Page What It Shows Why It Matters
Queues All queues, message count, consumer count See if messages are piling up (consumers too slow or dead)
Addresses Artemis's unified view of destinations (covers both queues & topics) Artemis uses "addresses" as the unified abstraction
Connections Active TCP connections from clients (your Spring Boot apps) See which services are connected right now
Sessions JMS sessions open on each connection Debug session leaks or concurrency issues
Infrastructure Detail: Artemis Addresses

Artemis has a concept that JMS doesn't: Addresses. An address is a routing name. It can route in two modes:

  • Anycast → behaves like a JMS Queue (point-to-point, one consumer gets the message)
  • Multicast → behaves like a JMS Topic (publish-subscribe, all subscribers get the message)

When you use JmsTemplate.convertAndSend("order.queue", ...), Artemis auto-creates an address named order.queue with anycast routing. You don't need to configure this manually.

Step 4: Send a Test Message from the Console

Let's prove the broker works before writing any Java code:

  1. In the web console, click Queues (or navigate to Artemis → Addresses)
  2. Click "Create Queue" (or "Create Address")
  3. Name: test.queue, Routing Type: Anycast
  4. Click on the new queue → "Send Message"
  5. Type a body: Hello from the console!
  6. Click Send
  7. Now click "Browse Messages" — you should see your message waiting in the queue

That message is now persisted on disk inside the Docker container. It will survive a broker restart. It will sit there until a consumer reads it.

Part 3: Useful Docker Commands

You'll use these throughout the course. Bookmark this section.

# Start the broker (if stopped)
docker start artemis

# Stop the broker (messages persist)
docker stop artemis

# View live logs
docker logs -f artemis

# Open a shell inside the container
docker exec -it artemis /bin/bash

# Use Artemis CLI to list queues
docker exec -it artemis /var/lib/artemis-instance/bin/artemis queue stat \
  --user admin --password admin

# Nuclear option: remove container + data (start fresh)
docker stop artemis && docker rm artemis

Knowledge Check

JMS is best described as:

  • A Java specification that defines messaging interfaces — brokers provide implementations
  • A specific messaging server developed by Apache for enterprise applications
  • A Spring Boot library that handles all messaging configuration automatically
  • A network protocol for sending messages between Java applications reliably

Which JMS object is NOT thread-safe and must not be shared across threads?

  • Session
  • ConnectionFactory
  • Connection
  • Destination

When your Spring Boot app calls jmsTemplate.convertAndSend("order.queue", message), what happens at the network level?

  • The message is serialized and sent over a TCP connection to the broker on port 61616
  • The message is written directly to a shared database that the consumer polls
  • Spring Boot makes an HTTP POST request to the broker's REST API endpoint
  • The message is stored locally in a file and the consumer reads it later

In ActiveMQ Artemis, what is the difference between an Address configured as "anycast" versus "multicast"?

  • Anycast delivers to one consumer (like a Queue); multicast delivers to all subscribers (like a Topic)
  • Anycast uses TCP protocol for delivery; multicast uses UDP protocol for delivery
  • Anycast sends messages synchronously to consumers; multicast sends them asynchronously
  • Anycast stores messages persistently on disk; multicast keeps messages only in memory

What port does the Artemis web management console run on?

  • 8161
  • 8080
  • 61616
  • 5672
