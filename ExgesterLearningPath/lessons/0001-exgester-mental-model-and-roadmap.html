Part 1: Why Exgester Exists (The Business Reality)

After the 2008 financial crisis, regulators worldwide decided they wanted to see the derivatives market. Laws like EMIR (EU), UK EMIR / FCA (Britain), ASIC (Australia) and CFTC / Dodd-Frank (US) all say roughly the same thing:

The Regulatory Deal

"Every time you trade a derivative, you must report the details to an authorized trade repository — accurately, in our prescribed format, within our deadline. Fail, and you're fined."

A bank like ANZ or Wells Fargo executes thousands of trades a day, each potentially reportable under multiple regimes at once (an Australian bank trading with an EU counterparty may owe both ASIC and EMIR reports). Doing this manually is impossible. Doing it wrong is expensive. That is the product: Cappitech regulatory reporting — and Exgester is the engine room.

Part 2: The Three-Stage Mental Model


  EXGESTER: THE MACHINE
  ═════════════════════

  ┌────────────┐     ┌──────────────────────────────┐     ┌──────────────────┐
  │ TRADE      │     │ DECISION ENGINE              │     │ REGULATORY       │
  │ EVENT      │ ──→ │                              │ ──→ │ SUBMISSION       │
  │            │     │ 1. Eligible for reporting?   │     │                  │
  │ JSON msg   │     │ 2. Which regimes? EMIR? ASIC?│     │ Formatted msg    │
  │ on an AMQ  │     │ 3. Enrich (LEI, UTI, venue)  │     │ per regime, sent │
  │ queue      │     │ 4. Validate all fields       │     │ downstream       │
  └────────────┘     └──────────────────────────────┘     └──────────────────┘
       edge                    pure core                        edge
   (messaging I/O)      (decisions, no I/O)               (messaging I/O)

Burn this in: messaging at the edges, decisions in the core. The core never talks to a queue, never logs-and-swallows, never surprises you. That separation is what makes Exgester testable — and it's a discipline called side-effect isolation that you'll practice in Week 2.

Part 3: The Railway (Preview of the Most Important Idea)

What happens when step 2 of the decision engine says "this trade is out of scope"? Or step 4 finds a missing LEI? Exgester does not throw exceptions for this. Business rejections aren't exceptional — they're half the job.

Instead, every pipeline step returns a Vavr Either<RejectionReason, Trade>: a value that is either a failure (Left) or a success (Right). Steps chain like railway segments:


  THE TWO-TRACK RAILWAY
  ═════════════════════

  Success track ──→ [eligibility] ──→ [regimes] ──→ [enrich] ──→ [validate] ──→ SUBMIT
                        │                │             │            │
                        ╰── Left ────────┴──── Left ───┴─── Left ───┴──→ REJECT
                            (reason)                                     (with reason)

  The FIRST failure switches the train to the bottom track.
  All remaining steps are skipped. The reason travels to the end.

One fold(...) at the end routes the train: submissions go downstream, rejections go to an audit/rejection queue. No try/catch pyramids, no null checks, no half-processed state. This is railway-oriented programming, and by Session 12 you will write these pipelines fluently.

Part 4: One Engine, Many Banks

Exgester serves ANZ, Westpac (WBC), Santander, Wells Fargo and more — from one codebase. Each client runs as its own deployment with its own Spring profile:

// A custom composed annotation — this is the real Exgester pattern
@Target(ElementType.TYPE)
@Retention(RetentionPolicy.RUNTIME)
@Profile("anz")
public @interface AnzProfile {}

// Beans annotated @AnzProfile exist ONLY when the app boots as ANZ
@Service
@AnzProfile
public class AnzEligibilityRules implements EligibilityRules { ... }

Add per-client YAML (application-anz.yml: which regimes are on, which queues to use, feature flags) and you get the multi-tenant architecture: common flows shared, client flows swapped in by profile. Week 4 is devoted to building this with your own hands.

Ground Rule

Never paste proprietary Exgester code into this workspace or into the agent. We learn on Mini-Exgester — an open reconstruction you build yourself. Validate its shapes against the real code at work, with your team.

Part 5: Your 5-Week Route

Week 1 — Modern Java. Immutability, generics, lambdas, streams, Optional, SOLID. Why first: Either<L,R> signatures are unreadable without generics fluency; pipelines are functions composed of functions.

Week 2 — FP & Vavr. Option, Try, Tuple, then Either and railway-oriented programming. You build the Mini-Exgester decision engine. The heart of the course.

Week 3 — Design Patterns. Strategy, Factory, Builder, Template Method, Chain of Responsibility, Composite — each landed in the engine, not in toy zoo examples.

Week 4 — Multi-Tenant Spring. Constructor injection, custom @Profile annotations, YAML config binding, Jackson deep-dive, JMS wired to the engine.

Week 5 — Testing & Quality. JUnit + AssertJ + Mockito, Cucumber BDD, Maven/JaCoCo/Checkstyle gates, Docker Compose, capstone assembly, final grill.

Check Your Understanding

A trade fails the eligibility check in step 1 of a 4-step railway pipeline. What happens to steps 2–4?

  • They are skipped; the Left rides to the end
  • They run anyway; the Left flag is checked last
  • They each throw and log its own exception
  • They run in parallel on the failure track

Why does Exgester avoid exceptions for business rejections like "trade out of scope"?

  • Rejections are normal outcomes, modeled as values
  • Exceptions are slower than returning any value
  • Spring Boot cannot catch checked JMS exceptions
  • Regulators forbid exception logging in engines

How does one Exgester codebase serve both ANZ and Wells Fargo with different flows?

  • Profile-gated beans plus per-client YAML config
  • Separate git branches maintained for each bank
  • Runtime if/else checks on a client name field
  • Each bank gets its own recompiled artifact

Where do side effects (queues, logging) belong in the Exgester architecture?

  • At the edges; the decision core stays pure
  • Inside each pipeline step for full auditing
  • In a global aspect that wraps every method
  • Nowhere; the engine avoids all side effects
